# 25 Oct 2026 — `ai_usage` table (AI cost per gym on the super admin Dashboard)

One row per AI call (AI plan, diet chart, client insights): gym, feature, tokens, cost in USD.
Written only by the server (server key bypasses RLS). Readable only by the super admin.
Gyms, partners, clients and logged-out visitors cannot read or write it.
`company_id` is a plain uuid (no foreign key) so deleting a company is never blocked by its AI history.

```sql
create table if not exists public.ai_usage (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  company_id uuid,
  user_id uuid,
  feature text not null,            -- 'plan' | 'diet' | 'insights'
  model text not null,
  input_tokens integer not null default 0,
  output_tokens integer not null default 0,
  cost_usd numeric(12, 6) not null default 0
);
create index if not exists ai_usage_company_created on public.ai_usage (company_id, created_at);

alter table public.ai_usage enable row level security;

revoke all on public.ai_usage from anon;
revoke all on public.ai_usage from authenticated;
grant select on public.ai_usage to authenticated;

create policy ai_usage_super_admin_read on public.ai_usage
  for select to authenticated
  using (public.get_my_role() = 'super_admin');
```

Run it once. If it is run again, the `create policy` line reports that the policy already exists; that is harmless (the transaction rolls back, nothing changes).

Check (as super admin in the app after one AI plan, or in the SQL editor):

```sql
select created_at, feature, input_tokens, output_tokens, cost_usd from public.ai_usage order by created_at desc limit 5;
```

Before this runs, AI features work as normal and nothing is recorded (a warning in the server log).
History starts from when this runs; earlier AI calls were never recorded.
