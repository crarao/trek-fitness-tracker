# 29 Oct 2026 — Leads / enquiry tracking (ROADMAP #52) — ALREADY RUN

**Status: run in Supabase (Mumbai project `coachboard-mumbai`) by Anand on 29 Oct 2026, before the leads app change.** Grants check confirmed: `authenticated` has INSERT, SELECT, UPDATE only; `anon` has nothing. This file records what was run; there is nothing left to run.

Why: today only confirmed members are tracked. Gyms and coaches want to track enquiries (walk-ins, Instagram DMs, referrals),
follow them up on WhatsApp, and convert them to members.

What it does (additive only, nothing existing is changed or removed):
- Creates one new table `public.leads`.
- Adds 3 lookup indexes and a small trigger that keeps `updated_at` current.
- Turns RLS on with **one rule per action** (lesson from #50 / #56: no overlapping rules):
  - read: staff (company admin + partner) of the gym read that gym's leads; super admin reads all
  - add: staff add leads to their own gym only, stamped with their own login (`created_by`)
  - update: staff update their own gym's leads only, and can't move a lead to another gym
  - **no delete rule and no delete permission.** A lead is never deleted: it is marked `lost` or `joined` (CLAUDE.md Rule #1).
- Logged-out visitors and clients get no access at all.
- Helpers are wrapped as `(select …)` so the login is checked once per query, not once per row (#50).
- Later, when the `coach` role ships (#40), add `'coach'` to the role lists in these three rules if coaches should see leads.

Columns:

| Column | Meaning |
|---|---|
| `company_id` | the gym / coach business (required) |
| `name` | required |
| `phone` | optional (an Instagram enquiry may not have one yet); the app checks it against members and open leads |
| `source` | free text the app fills from chips: walk_in, instagram, referral, website, whatsapp, other |
| `interest` | free text from chips: membership, pt, trial, other |
| `status` | `new` → `trial` → `joined` / `lost` (checked by the database) |
| `follow_up_date` | next follow-up (date only) |
| `last_contacted_at` | set when staff tap WhatsApp follow-up |
| `lost_reason`, `notes` | free text |
| `converted_profile_id` | the member created by "Convert to member" |
| `created_by` | staff login that added it (defaults to the logged-in user) |
| `created_at`, `updated_at` | timestamps |

Foreign keys follow the app's own delete features (not something Claude runs):
- deleting a **company** in super admin also removes its leads (`on delete cascade`), like its members;
- deleting a **member** or a **staff login** keeps the lead and just clears the link (`on delete set null`).

## SQL

```sql
-- 1. Table
create table if not exists public.leads (
  id                   uuid primary key default gen_random_uuid(),
  company_id           uuid not null references public.companies(id) on delete cascade,
  name                 text not null,
  phone                text,
  source               text,
  interest             text,
  status               text not null default 'new'
                         check (status in ('new','trial','joined','lost')),
  follow_up_date       date,
  last_contacted_at    timestamptz,
  lost_reason          text,
  notes                text,
  converted_profile_id uuid references public.profiles(id) on delete set null,
  created_by           uuid default auth.uid() references public.profiles(id) on delete set null,
  created_at           timestamptz not null default now(),
  updated_at           timestamptz not null default now()
);

-- 2. Indexes (lists by status, follow-ups due, duplicate-phone check)
create index if not exists leads_company_status_idx    on public.leads (company_id, status);
create index if not exists leads_company_follow_up_idx on public.leads (company_id, follow_up_date);
create index if not exists leads_company_phone_idx     on public.leads (company_id, phone);

-- 3. Keep updated_at current
create or replace function public.leads_set_updated_at()
returns trigger language plpgsql set search_path = public as $$
begin
  new.updated_at := now();
  return new;
end;
$$;
revoke execute on function public.leads_set_updated_at() from public, anon, authenticated;

create trigger leads_set_updated_at
  before update on public.leads
  for each row execute function public.leads_set_updated_at();

-- 4. RLS: one rule per action
alter table public.leads enable row level security;

create policy "Leads read: staff own gym, super admin all" on public.leads
  for select to authenticated
  using (
    ((select public.get_my_role()) in ('company_admin','partner')
      and company_id = (select public.get_my_company_id()))
    or (select public.get_my_role()) = 'super_admin'
  );

create policy "Leads add: staff own gym" on public.leads
  for insert to authenticated
  with check (
    (select public.get_my_role()) in ('company_admin','partner')
    and company_id = (select public.get_my_company_id())
    and created_by = (select auth.uid())
  );

create policy "Leads update: staff own gym" on public.leads
  for update to authenticated
  using (
    (select public.get_my_role()) in ('company_admin','partner')
    and company_id = (select public.get_my_company_id())
  )
  with check (
    (select public.get_my_role()) in ('company_admin','partner')
    and company_id = (select public.get_my_company_id())
  );

-- 5. Explicit grants: signed-in users may read, add, update. No delete. Logged-out: nothing.
revoke all on public.leads from anon, authenticated;
grant select, insert, update on public.leads to authenticated;
```
