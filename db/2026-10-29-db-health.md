       pg_get_function_result(p.oid) as returns, r.rolname as owner
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
join pg_roles r on r.oid = p.proowner
where n.nspname = 'public'
  and p.proname in ('get_my_role', 'get_my_company_id', 'protect_company_columns',
                    'protect_profile_columns', 'rls_auto_enable');

## Step 2 — nobody calls the trigger functions directly

Triggers still fire as before: Postgres doesn't check call permission when a trigger fires.
This only stops someone calling the function by hand through the API.

```sql
begin;
revoke execute on function public.protect_company_columns() from public, anon, authenticated;
revoke execute on function public.protect_profile_columns() from public, anon, authenticated;
revoke execute on function public.rls_auto_enable() from public, anon, authenticated;
commit;
```

If the `rls_auto_enable` line errors (for example "must be owner"), run the transaction again
without that line: it belongs to Supabase, not to us.

**Test:** as a coach, upload a logo or banner (company update still works and is still limited
to logo / banner). As a coach, edit a client's name (profile update still works). As a client,
edit your own profile (still works; you still can't change PT status).

**Undo:**
```sql
grant execute on function public.protect_company_columns() to public, anon, authenticated;
grant execute on function public.protect_profile_columns() to public, anon, authenticated;
grant execute on function public.rls_auto_enable() to public, anon, authenticated;
```

## Step 3 — logged-out visitors can't call the helpers

**Step 0 B (run 29 Oct) returned 4 rules** that apply to every role (`{public}`, which includes
logged-out visitors) and call the helpers:

| Table | Rule | Action |
|---|---|---|
| companies | Users can read own company | SELECT |
| profiles | Company admin can delete client profiles | DELETE |
| profiles | Company admin can update client profiles | UPDATE |
| logged_sessions | Company admin can delete client sessions | DELETE |

If the helpers were simply revoked from logged-out visitors, Postgres would still check these
rules for a logged-out request and stop with "permission denied for function". The branded
login page reads `companies` while logged out, so it would break.

So Step 3 first narrows those 4 rules to signed-in users (`ALTER POLICY … TO authenticated`,
edited in place, nothing dropped). A logged-out visitor never matched them anyway: with no login,
`get_my_role()` / `get_my_company_id()` return nothing. Logged-out access to company branding
comes from the separate rule "Public can read company branding" (role `anon`), which is untouched.

```sql
begin;
alter policy "Users can read own company" on public.companies to authenticated;
alter policy "Company admin can delete client profiles" on public.profiles to authenticated;
alter policy "Company admin can update client profiles" on public.profiles to authenticated;
alter policy "Company admin can delete client sessions" on public.logged_sessions to authenticated;

revoke execute on function public.get_my_role() from public, anon;
revoke execute on function public.get_my_company_id() from public, anon;
grant execute on function public.get_my_role() to authenticated;
grant execute on function public.get_my_company_id() to authenticated;
commit;
```

**Check after (read-only):** run Step 0 B again → **no rows**.

**Test (private / incognito window, logged out):** open a gym's branded login link → the gym's
name, logo and banner show; plain `/login` works; the landing page contact form still sends.
**Test (logged in):** coach → member list loads, edit a client's name, delete a test session;
client → their screen loads.

**Undo:**
```sql
begin;
grant execute on function public.get_my_role() to public, anon;
grant execute on function public.get_my_company_id() to public, anon;
alter policy "Users can read own company" on public.companies to public;
alter policy "Company admin can delete client profiles" on public.profiles to public;
alter policy "Company admin can update client profiles" on public.profiles to public;
alter policy "Company admin can delete client sessions" on public.logged_sessions to public;
commit;
```

## Step 4 — RLS rules check the login once per query, not once per row

Rather than retyping ~15 rules by hand, this query **writes the statements for you** from the
live rules. It wraps `auth.uid()`, `auth.jwt()`, `auth.role()`, `get_my_role()` and
`get_my_company_id()` in `(select …)`, which Postgres then runs once per query. The rule's
meaning doesn't change. `ALTER POLICY` edits a rule in place; nothing is dropped.

**4a. Generate (read-only):**
```sql
with p as (
  select schemaname, tablename, policyname, qual, with_check,
         regexp_replace(regexp_replace(coalesce(qual, ''),
           '(?<!SELECT )(auth\.(uid|jwt|role)\(\))', '(select \1)', 'g'),
           '(?<!SELECT )((public\.)?get_my_(role|company_id)\(\))', '(select public.get_my_\3())', 'g') as new_qual,
         regexp_replace(regexp_replace(coalesce(with_check, ''),
           '(?<!SELECT )(auth\.(uid|jwt|role)\(\))', '(select \1)', 'g'),
           '(?<!SELECT )((public\.)?get_my_(role|company_id)\(\))', '(select public.get_my_\3())', 'g') as new_check
  from pg_policies
  where schemaname = 'public'
)
select tablename, policyname,
  format('alter policy %I on %I.%I%s%s;', policyname, schemaname, tablename,
    case when qual is not null then ' using (' || new_qual || ')' else '' end,
    case when with_check is not null then ' with check (' || new_check || ')' else '' end) as run_this,
  format('alter policy %I on %I.%I%s%s;', policyname, schemaname, tablename,
    case when qual is not null then ' using (' || qual || ')' else '' end,
    case when with_check is not null then ' with check (' || with_check || ')' else '' end) as undo_this
from p
where new_qual <> coalesce(qual, '') or new_check <> coalesce(with_check, '')
order by tablename, policyname;
```

**Before running anything:** use the results grid's **Export → CSV** (or copy) and save the file
somewhere safe. The `undo_this` column is the exact rule text as it is today.
Send a screenshot of a few `run_this` rows if you'd like them checked first.

**4b. Run:** copy every `run_this` value into a new SQL tab, add `begin;` at the top and

**Test:** run the Step 1 tests again for all three roles, plus a coach on a client of another gym

**Undo:** run the saved `undo_this` lines inside `begin; … commit;`.

## Step 5 — indexes for the app's lookups

Every page filters by these columns (members of a gym, plans/sessions of a client, feedback of a
session). Adds indexes only; existing ones with the same name are skipped. Tables are small,
so this takes seconds.

```sql
create index if not exists profiles_company_id on public.profiles (company_id);
create index if not exists memberships_profile_id on public.memberships (profile_id);
create index if not exists memberships_company_id on public.memberships (company_id);
create index if not exists weekly_plans_client_week on public.weekly_plans (client_id, week_start);
create index if not exists logged_sessions_client_date on public.logged_sessions (client_id, session_date);
create index if not exists logged_sessions_weekly_plan_id on public.logged_sessions (weekly_plan_id);
create index if not exists logged_sessions_logged_by on public.logged_sessions (logged_by);
create index if not exists session_feedback_session_id on public.session_feedback (session_id);
```

If Step 0 C already showed an index on the same column(s) under another name, skip that line
(a duplicate index works but costs a little on every save).

**Test:** owner dashboard and a client page load as before. Refresh the Performance Advisor.

**Undo:** removing an index is a `DROP INDEX`, so per Rule #1 it is only done with Anand's
explicit approval; an extra index never changes what the app reads or writes.
